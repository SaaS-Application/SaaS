# Attendance behavior

Attendance rules belong to a company and are evaluated in that company's configured IANA time zone. New companies use 09:00-17:00, 480 required working minutes, a 15-minute grace period, a 240-minute half-day threshold, a 30-minute overtime threshold, Saturday/Sunday weekly holidays, and UTC until an administrator changes the rules.

## Status and calculation policy

- Each record has exactly one status. `PRESENT`, `LATE`, and `HALF_DAY` are derived from punches when both check-in and check-out are present. A short day (`worked minutes < half-day threshold`) is `HALF_DAY`; otherwise a check-in later than `work start + grace period` is `LATE`; all other completed work is `PRESENT`.
- `lateArrival` is a separate indicator, so a `HALF_DAY` can also be late. The status remains `HALF_DAY` when both conditions apply.
- `ABSENT` and `HOLIDAY` are manually selected statuses and cannot include punch times. `WEEK_OFF` may contain punches when an employee works on a configured weekly holiday; it remains `WEEK_OFF`. `ON_LEAVE` and `HALF_DAY` entries generated by Leave Management are linked to their approved leave request and are not editable through attendance corrections. See [`LEAVE.md`](./LEAVE.md) for leave approval, cancellation, and balance behavior.
- Early departure means a same-day check-out before the configured work end. Overtime is the minutes beyond required working minutes, and is reported only when that excess is at least the configured overtime threshold.
- Work start must precede work end; overnight shifts are not supported. The grace period is inclusive: a check-in exactly at the end of the grace period is not late.

Check-in/check-out instants are stored alongside company-local wall times and the time-zone ID captured for the record. Company-local times in a daylight-saving gap are rejected for manual records. For an ambiguous repeated local time, manual entry uses the earlier valid offset; real employee punches retain their captured instant.

Employee check-ins and check-outs are immediately usable records and do not require approval. HR/Admin manual entries and corrections start in `PENDING`; approval or rejection records the reviewing user. A correction returns the record to `PENDING`. Employees can only punch for the current company-local date and cannot edit records through management APIs.

## Existing MySQL installations

The project has no Flyway/Liquibase migration history; Hibernate `ddl-auto: update` is the existing schema mechanism. Do not initialize Flyway against an uninspected production schema or execute either manual script blindly. First take and verify a restorable backup, stop the application, inspect `information_schema`, and confirm table engines, column types, existing columns/constraints, duplicate attendance dates, and employee/company/tenant consistency. Both scripts are one-time migrations; if the schema is partly migrated, apply only the missing reviewed statements rather than rerunning the whole file.

For the original attendance table, review every preflight query in [`phase4-attendance-mysql.sql`](./src/main/resources/db/manual/phase4-attendance-mysql.sql). Resolve duplicates or orphan/mismatched tenant rows without deleting attendance records. The migration adds a unique employee/date key and restrictive composite foreign keys, so existing data must satisfy those constraints first. Review any existing `attendance_rules` table before creating one. New timestamp columns are nullable; timezone metadata defaults to UTC only if that is correct for historical wall-clock punches. Set an appropriate default before applying the migration or backfill the correct timezone for existing rows before enabling the application.

For employee login identity, apply [`phase4-1-employee-user-link-mysql.sql`](./src/main/resources/db/manual/phase4-1-employee-user-link-mysql.sql) only after confirming `employees.user_id` and its named constraints do not already exist. It adds a nullable unique account reference and a restrictive FK; it does not backfill or change existing profile data. The final query is for review only. Validate each candidate with the company owner and link it using `POST /api/company-admin/employees/{employeeId}/account` as a Company Admin or HR Admin. The endpoint requires an active `EMPLOYEE` account, matching email, and exact company and tenant ownership. Duplicate or ambiguous candidates must be resolved manually; do not run a broad email-based `UPDATE`.

Employee self-service never creates account links. An unlinked employee receives an authorization error and must contact a Company Admin or HR Admin to complete the explicit link operation. After linking, employee and attendance self-service resolve the profile by authenticated user ID. Email matching is only a validation on the authorized linking operation; it never creates a link by itself.

Flyway is deferred: there is no existing migration history to baseline against and the current MySQL schema cannot be authenticated/inspected in this environment. Introducing a migration runner before a verified schema inventory could make startup fail or cause an unsafe baseline. Keep the reviewed manual scripts for this release; adopt Flyway after a DBA-reviewed baseline and tested restore/upgrade rehearsal. Production continues to have Hibernate `ddl-auto: update`; use a planned schema-management change before relying on migration-only DDL.
